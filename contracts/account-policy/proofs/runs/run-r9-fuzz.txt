=== 1. What changed in the harness (release 9)

All three targets compile and are correct on release 9:
- fuzz_api: upgrade_check takes (from_version, code_hash); the RS-2 literal gas price is 1_000_000_000 yocto/gas (W_GAS_PRICE
  in fuzz_api, the literal in contract.rs sub-target 0; was 2e8); SEQ_KEYS carries the finishing marker and the release list.
- recovery_seq (release 7's target, its oracle unchanged): finish_recovery now only adds the new key, so the target delivers
  its callback on_recovery_key(new_key, ready_at_ns, asked_at_ns) at once with the add Successful (release 7's one-step
  world); its oracle then checks the finished state exactly as before.
- contract: the gas price literal; drive_upgrade_migration calls upgrade_check(6, None).
- recovery_seq_wide (drive_recovery_wide), widened. Input: 3 config bytes, then up to 64 operations of 4 bytes (kind, signer,
  argument, extra); max_len 259. New in the start state: an UNSEALED phone list (an older account: keys learned as phones),
  release 0 on the account's list or not, device 9's key missing on NEAR (a release-7 account, FB-3's repair case).
  Signers: 10 (round 8's 9 plus the waiting or finishing recovery's new key). Operations: 18 kinds (round 8's 17, with:
   4 finish_recovery: its add's outcome is the op's top bit (the storage edge) or NEAR's own rule (an add of a key that
     exists fails); the callback is scheduled, not run;
  14 a callback, delivered at any later moment, after any other calls (the phone's stop, a device's refusal, a co-signed
     removal of the yes-device, new words, another finish...): FB-3's on_second_device_key or release 9's on_recovery_key,
     with the outcome its receipt had; or (extra bit 6) a finish's callback LOST (it ran out of its reserved gas: nothing it
     does happens). Any callback may come next, but one key's callbacks come in the order made;
  15 upgrade of a listed / unlisted / asked-for release (three hashes), or upgrade_check(6/7/8/9, with or without a hash);
  17 refill_recovery_key from any signer; AllowRelease and Upgrade run / approve / decline / cancel through ops 5-8.)
- A model of NEAR's access keys: every receipt of every accepted call is replayed in the order made, all or nothing (a
  delete of a missing key or an add of a present key fails the receipt), a callback's receipt with the outcome the fuzzer
  chose; each key carries its method set (phone / second device / words, read from the literal method names).

The shadow oracle's NEW rules (literals only, never the contract's helpers), on top of every release-7/8 rule (kept):
- R8-RS1: finish_recovery deletes nothing but its own new key (RT3's fix) and a stale finish's key (RT3-b's fix), adds the
  new key with the phone's methods, schedules exactly one callback for (key, ready_at, now), and changes no state; the
  shadow's phone, devices, list, recovery and freeze do not move until the callback; old phone keys deleted by anything but
  a callback that saw the add succeed = "the phone's key was deleted while it is the phone"; after a failed add the
  callback makes no receipt and changes nothing (the old phone still acts, the recovery still waits); the callback
  completes the recovery iff the add succeeded AND the same recovery (key, ready_at) still waits AND it may finish by the
  oracle's own rule (delay, fallback, a device of age's yes); a succeeded add for a recovery that did not finish deletes
  exactly the new key, unless a role holds it; a callback whose finish was superseded (another asked_at on record) does
  nothing at all; a second finish within the hour is refused, and liveness: the words' finish of a due recovery (no finish
  asked less than an hour ago) succeeds;
- RT3: a finish's add fails only at the storage edge, never because its key is already on NEAR;
- NEAR's keys follow the records (receipts replayed): the account always keeps a phone key on NEAR with the phone's
  methods; the words' key is on NEAR with the words' methods; every recorded device's key is on NEAR as a device (but one
  whose add's callback is still on its way); a role's key never carries another role's methods; and a key on NEAR with no
  role (a lost finish's key, an unrecorded device's: O-r9-2) must be refused by the contract's own gate for its methods
  (device_gate / second_device_gate / words_gate, probed after every call);
- the new key never acts as the phone before its recovery completed: an owner method accepted from it is a violation, and
  after every call the device gate is PROBED (on a copy) with the waiting / finishing recovery's key (must refuse) and with
  the current phone (must accept, also while finishing and after a failed add);
- allowlist: upgrade(h) places AllowRelease{h, now} unless h is listed or an AllowRelease for h waits (then Upgrade); the
  list only grows when an AllowRelease runs co-signed by a device of age or at >= asked + max(fallback, floor), keeps at
  most 4 (oldest out), and is set to [h] / [] by upgrade_check; an Upgrade runs only for a listed hash; a switch
  (UseGlobalContract) is emitted only by an Upgrade's run, only for a listed hash, with upgrade_check's arguments
  {"from_version": 9, "code_hash": h}; the contract's list cell equals the shadow's after every call;
- upgrade_check(from, h): never refused, changes no policy state, renews every recorded device's key (delete-and-add) iff
  from < 9, makes no receipt from 9;
- refill_recovery_key: accepted only from a recorded second device of age while words exist, and then exactly one receipt
  that deletes and re-adds the words' key with the words' methods, no state change; liveness: such a device's refill succeeds;
- an unsealed list learns a phone exactly when the contract's gate would (not a device, not the words, not the recovery's
  or finishing key, fewer than 8 keys), and the finish seals it.

=== 6. Findings on the earlier release-9 sources (both FIXED in r9-frozen-3)

RT3 (the sandbox red team's; reproduced independently by this oracle on r9-frozen-2, seed s25). Low/Medium, liveness. A
finish whose add of the new key succeeded but whose callback never ran (it can run out of its reserved gas) leaves the key
on NEAR; the words' retry an hour later adds it again, NEAR refuses an add of a key that exists, and the recovery can never
complete. Sequence: words start_recovery(K5); the delay; finish_recovery (K5 added); the callback is lost; finish again
(refused under the hour); +1 h; finish again. The oracle: "RT3: the finish's add of key 5 fails (the key is already on
NEAR: Some(Phone)), so this recovery can never complete". Input (hex, seed s25):
  000010 00010000 10000700 04010000 0e000040 04010000 10000100 04010000 0e000000 0d000000
Fixed in r9-frozen-3: the finish deletes the new key in a receipt of its own, then adds it in a receipt chained after the
delete (add_after_delete), then the callback; the callback carries asked_at_ns and acts only for the finish on record.

RT3-b (found by THIS round's widened oracle on r9-frozen-2, from a hand-written seed written while reading RT3, not by a
fuzzing run; reported to the lead 10:22). Low, theoretical (needs a callback that runs out of its 30 Tgas, and an UNSEALED
phone list, i.e. an account that has never finished a recovery). Sequence (seed s26):
  unsealed list, no second device, words 4.
  1 words: start_recovery(K5); the delay; finish_recovery -> K5 added to NEAR with the phone's methods
  2 the callback is lost: the finishing record (K5) stays
  3 phone: cancel_recovery -> with no device of age the recovery ends at once
  4 words: start_recovery(K6); the delay + 1 h; finish_recovery -> the record is replaced by K6's
  5 K5 now holds no role and is no recovery's key, but it is on NEAR with the phone's methods, and the device gate of an
    unsealed list LEARNS it as a phone: "key 5, on NEAR with the phone's methods from a finish whose callback never ran,
    passes the device gate though no recovery to it completed".
  So whoever chose K5 (the words' holder) gets a phone after the phone stopped that recovery. On a sealed list the gate
  refuses it (an orphan key only). Input (hex, seed s26):
  002010 00010000 10000700 04010000 0e000040 03000000 00010100 10000700 10000100 04010000 0e000000 0d090000 0d050000
Fixed in r9-frozen-3: a finish that replaces a stale record of ANOTHER key deletes that key first (its own receipt).
On r9-frozen-3 both seeds run clean (the stale key is deleted; the retry's delete-then-add succeeds and its callback
completes the recovery), and the controls RT3rev / RT3b / ASKED (section 5) put each fix back out.

- the space is preset-driven: 5 band presets, 11 spend presets, keys 1-13, three release hashes, delays of 1/2/3/7/30 days;
  the 24-hour spending history only gives a lower bound on a spend's level;
- NEAR is a model: each call's receipts run right after it, in the order made, all or nothing; an add fails at the storage
  edge only when the fuzzer says so (one bit), and otherwise only by NEAR's own rule (the key exists); balances, gas and
  storage are not modelled; a lost callback is modelled only for the finish's callback (FB-3's never run out of gas here);

  call; a role's method set is read from the literal method names (phone: "execute"; device: "approve_recovery"; words:
